MY IDEA

最近看到QQ的ai助理和其他非官方的QQ群消息总结，发现貌似可以把消息总结和行程管理结合起来。类似于老板的秘书。难道我也可以有我自己的秘书吗？！

分析

问题：平时群太多，容易看漏东西，比如课程作业安排，作业改动，考试安排，学院通知等等。

同类项目：

  1. 元宝总结：和QQ深度融合，格式规范，可以标签指引到相关对话与图片，方便用户亲自确认信息，但是微信没有相关功能
  2. WeFlow：github开源项目可能可以有方便的接口，只有统计功能不能分析

功能（重要性递减）：

  1. 能将QQ群聊（对话）的聊天记录分析并且总结重要事项
  2. 能将微信群聊（对话）的聊天记录分析并且总结重要事项（微信更难获取聊天记录）
  3. 能够分析出Deadline并且按照时间排序
  4. 能够通过手机自带的日历进行自动安排
  5. 能够部署云端
  6. 能够通过类似公众号（我试过相关TODO list产品）来提醒

技术：

  1. 读取QQ群聊消息
  2. deepseek/qwen api分析消息
  3. 读取微信群聊消息（最难）
  4. 根据格式输出内容
  5. 根据手机日历api进行写入日程
  6. 云端部署

AI项目分析报告（仅供参考）

课程群消息智能分析与日程管理系统项目报告

1. 项目概述

背景：学生群体面临课程群过多、消息碎片化严重的问题，导致作业 Deadline、考试安排、学院通知等重要信息容易被遗漏。
目标：构建一个自动化系统，能够读取聊天记录，利用 AI 提取关键事项，并同步至手机日历及发送提醒。
核心转变：基于安全性、成本及隐私考量，项目从最初的“云端实时机器人”调整为”本地每日批量分析“模式。

2. 核心约束与设计原则

为确保项目可落地且安全，遵循以下原则：

  1. 账号安全最高优先级：严禁在主号上使用协议机器人（如 NAPCat），严禁使用高风险 Hook 方案。只使用官方客户端本地数据。
  2. 单账号限制适配：适配课程群“仅限主号加入”的限制，不依赖小号监听。
  3. 本地化部署：数据不出本地局域网，保护隐私，节省服务器成本。
  4. 简化实时性：接受“每日一次”的批量处理模式，换取极高的稳定性和安全性。

3. 技术栈选型 (Technology Stack)

模块选型理由
开发语言Python 3.10+生态丰富，AI 库支持好，脚本编写快。
消息源获取WeChatMsg / 官方导出微信：使用开源工具解密本地 DB；QQ：使用官方消息管理器导出或类似解密工具。避免协议登录。
AI 分析引擎DeepSeek-V3 API性价比高，逻辑推理能力强，适合信息提取。支持本地 Ollama 作为隐私备选。
数据存储SQLite / JSON本地轻量级数据库，无需部署 MySQL/PostgreSQL。
任务调度Windows 任务计划程序系统原生支持，无需额外部署 Celery/Redis，稳定可靠。
日历格式iCalendar (.ics)通用标准，iOS/Android/Outlook 原生支持订阅或导入。
通知推送SMTP 邮件 / 企微 Webhook邮件最稳定且无需额外配置；企微 Webhook 可实现微信内推送。
运行环境Windows PC学生主力设备，无需额外购买服务器或常开旧手机。

4. 系统架构设计 (System Architecture)

采用 本地单机闭环架构，数据流如下：

5. 迭代路线图 (Iteration Roadmap)

从最小可行性产品 (MVP) 到最终完善产品，分四个阶段实施。

第一阶段：MVP 验证 (手动 + 核心分析)
  • 目标：验证 AI 能否准确从聊天记录中提取作业和 Deadline。
  • 功能：
    1. 手动导出：用户手动在 PC 微信/QQ 导出当天群聊天记录为文本/HTML。
    2. 脚本分析：运行 Python 脚本，读取文件，调用 DeepSeek API 分析。
    3. 控制台输出：直接在屏幕打印总结出的任务列表。
  • 耗时：3-5 天。
  • 交付：一个可运行的 Python 脚本，确认 AI 提取准确率 > 90%。
第二阶段：自动化数据获取 (半自动)
  • 目标：免去手动导出文件的步骤，实现本地数据自动读取。
  • 功能：
    1. 集成提取工具：集成 WeChatMsg 等库的接口，脚本自动获取本地 DB 解密后的消息。
    2. 定时任务：配置 Windows 任务计划程序，每天固定时间（如 22:00）自动运行脚本。
    3. 邮件推送：脚本运行结束后，通过 SMTP 发送总结邮件到用户手机。
  • 耗时：1-2 周。
  • 交付：完全后台静默运行，每天收到一封邮件总结。
第三阶段：日历同步与多通道提醒 (完善体验)
  • 目标：将任务写入日历，并增加紧急提醒。
  • 功能：
    1. ICS 生成：脚本生成 .ics 文件，自动同步至 OneDrive/iCloud 公共文件夹，手机日历订阅链接。
    2. 去重逻辑：数据库记录已处理消息 ID，避免重复添加日程。
    3. 企微推送：接入企业微信 Webhook，实现微信内的卡片消息提醒。
  • 耗时：1-2 周。
  • 交付：手机日历自动更新，微信收到提醒，形成完整闭环。
第四阶段：隐私增强与本地化 (可选优化)
  • 目标：彻底杜绝聊天记录出网，增强隐私。
  • 功能：
    1. 本地大模型：若 PC 显存足够 (>=8GB)，部署 Ollama + Qwen2.5-7B，替换云端 API。
    2. 简易 Web 面板：使用 Streamlit 搭建本地网页，用于手动修正 AI 提取错误的任务。
  • 耗时：视硬件条件而定。
  • 交付：100% 本地隐私保护，可人工干预修正。

6. 风险评估与应对 (Risk Management)

风险点可能性影响应对策略
本地 DB 加密变更中高关注 WeChatMsg 等开源项目更新；备选方案改为“手动导出文件”模式。
电脑关机/休眠高中任务计划程序设置“唤醒计算机运行”；或设置“错过时间后立即补跑”。
AI 提取错误中中邮件/通知中附带“原文链接”或“消息截图”；保留人工确认环节（初期）。
隐私泄露低高默认调用 API 前进行本地脱敏（替换姓名/学号）；最终阶段改用本地大模型。
网络波动中低脚本增加重试机制；API 调用失败时发送报错邮件而非静默失败。

7. 结论与建议

本项目经过需求收敛与技术选型调整后，已具备极高的可行性。

  1. 核心优势：彻底规避了主号封号风险，零服务器成本，隐私可控。
  2. 关键成功因素：在于本地数据提取的稳定性（依赖于开源社区对微信/QQ 本地协议的维护）以及AI Prompt 的调优。
  3. 启动建议：
    • 立即开始第一阶段：不要纠结架构，先手动导出一次聊天记录，用 DeepSeek 测试一下提取效果。如果 AI 能看懂，项目就成功了一半。
    • 保持低调：即使本地部署，也建议不要频繁大规模读取数据，避免触发 PC 客户端的安全风控。
    • 兜底方案：无论系统多完善，手机端的“关键词通知”永远不要关闭，作为最后一道防线。

此方案是在当前腾讯生态限制下，个人开发者能做到的最安全、最经济、最可持续的解决方案。

基于第一次第二次的完成实现了LLM处理消息和Caldav上传日程的两者耦合，并且通过watermark记录和补充上下文实现了可逐次增量分析消息记录的功能。优化了文件结构。已经达到可用的程度。存在的问题是QQ消息的导出仍然比较繁琐，LLM分析大段的文本仍然有不准确的情况。

对比

对比两次的分析结果。首先关于正确性。正确性都是100%，没有出现时间错误和事件错误。那么两者的最大区别就在于事件的数量了。全量分析中并没有把各种作业的补交放在事件中，所以会少很多事件。我个人觉得这个是有必要放在事件里的。

不过在之前的测试中，全量分析是有可能将补交算到事件中的，只不过概率比较小罢了。

至于原因的话，应该就是LLM自己的问题和我写的prompt的问题了。不过我计划是每天定时导出QQ群的消息，对于课程群来说，一天的消息应该不会太多，每天的记录分析应该都会比较详细。不过还是有必要以后再完善一下prompt。

计划

完善prompt，做几个toolcall，尽自己所能做一个agent。

最后

这周听了一个老师讲的很有意思的一句话，大概是说，LLM肯定不会取代真人，但它肯定会对一些重复性工作产生冲击，它的应用范围取决于这个工作到底能不能接受LLM所带来的误差。比如说，有的时候LLM并不认为补交算作一个DeadLine事件（在我的prompt写得非常简略的情况下），也许我就因此而失去了补交的机会。在我的这个项目中，我选择在格式化消息记录，导出事件，是否同意同步至日历三个步骤中设置了人工审查节点，让人来检查误差和承担决策的责任。
